# Hand raises API + room UI

This backend requires the confirmed viewer identity contract `viewer-<registration_id>` issued by the token endpoint. The room UI (viewer + host) is described at the end of this document.

| Endpoint | Caller | Outcome |
|---|---|---|
| GET /w/:slug/hand_raises | Confirmed registration for this published webinar | Own active hand in `hand_raise`, or null; never creates a request or exposes other viewers |
| POST /w/:slug/hand_raises | Confirmed registration for this published live webinar | 201, own active hand; repeated POST returns the same hand |
| DELETE /w/:slug/hand_raises | Same registration | 204; lowers only its own hand, revoking publication first when necessary |
| PATCH /w/:slug/participation | Same registration (JSON, CSRF) | 200 `{ participation }` (the kept choice); records once (first choice wins) the room-entry choice `spectator`/`participant` of THIS browser's registration only (`ParticipationsController`); 403 `registration_required` without it, 422 `invalid_participation` otherwise |
| GET /webinars/:webinar_id/hand_raises | Owning host | Active waiting/granted/in-flight/uncertain hands, ordered by raised_at |
| POST /webinars/:webinar_id/hand_raises/:id/grant | Owning host, published live webinar | Updates viewer-ID publication to true; records granted_at only after RPC success |
| POST /webinars/:webinar_id/hand_raises/:id/revoke | Owning host | Updates publication to false; records revoked_at only after RPC success |

JSON exposes id, registration_id, name, `wants_video` (the registration chose `participant`), state, raised_at/granted_at/revoked_at and a generic error code. It never includes registration email/token. Unauthorized registration gets 403; another host's resource is 404; non-live grant/raise is 409; RPC failures are 502 permission_update_failed. Cookie/CSRF protections are inherited from Rails; supplied participant identities and registration IDs are ignored.

With a current consent, granting an already granted hand pushes the permission to LiveKit again (a participant back with a token issued before the grant). Who may publish has ONE rule, `PublishPermission`: for a viewer, a current image consent AND a granted active hand, with the limited `PublishPermission::SOURCES`. Granting a hand without consent marks it granted and opens nothing; the room shows the consent window, and its POST opens the publication (`HandRaiseControl#open_publication`). The viewer token itself carries `canPublish` while that rule holds (`PublishPermission#token_grant`): reloading the page no longer takes the floor away. Any token that publishes outside the hosts by right gets the short `LivekitTokenService::COHOST_TTL` (15 min, `LivekitTokenService.ttl_for`), and the `participant_joined` webhook guard realigns the permission on the CURRENT rule under the hand-raise lock (`PublishPermission#reconcile_on_join`): a floor taken away, a hand closed or a consent withdrawn is not given back by an older token on reconnection. A missed closing is retried by `PublishingRevocationJob`, which re-reads the whole rule under the same lock before closing (`HandRaiseControl#close_publication_unless_allowed`): a viewer with consent but without the floor, back with an older token that publishes, is closed; someone allowed again in the meantime keeps the right; a waiting hand stays raised.

Pre-declared hand: a registration that chose `participant` on the public link enters the room with a waiting hand, raised by the token endpoint on its first entry only (`HandRaiseControl#raise_declared_hand`; never raised again once lowered, refused or returned; skipped when not live, without room access or unpaid). The host admits it with the usual grant.

Room-entry choice: a registration that never chose (`registrations.participation_chosen_at` empty — e.g. a partner site that does not send `participation`) sees « J'observe » / « Je participe » before the room is mounted, pre-selected on its current value (`webinars/room.html.erb`, `rooms/participation_choice.js`), once per webinar; never the hosts. A choice made on a form that asks for it (public registration, private participants link, hand-over confirmation, API with `participation`) is dated at creation and not asked again. The choice is saved before the token request (`Registration#choose_participation!`, first choice wins: a stale second tab changes nothing) and the hand follows it (`HandRaiseControl#follow_participation`): `participant` raises a waiting hand, even after an older one was lowered (a new deliberate choice); `spectator` lowers a hand still waiting, never a granted floor. It grants nothing: publishing still needs the host's grant and the image consent. Changing one's mind afterwards goes through « Lever / Baisser la main ». Visible wording (product decision, 10/11): the two options are « J'observe — j'ai le chat » / « Je participe — caméra et micro », never a raised hand nor an admission; while a `wants_video` hand waits, the room only says « On t'ouvre la caméra et le micro dans un instant » (voice key `webinars.participation_choice.waiting`) with a « Je préfère observer » button that lowers it. The régie highlights these hands (accent rule on the entry, « N participant·e(s) à admettre en caméra et micro » above the queue).

Raise and grant also require `webinar.free? || registration.paid_confirmed?`; this includes zero-price webinars belonging to a paid pack. An unpaid participant gets 403 `payment_required`, and the host cannot bypass payment when granting. Lower/revoke remain available to remove permissions.

A viewer removed from the room from the régie (`POST /webinars/:webinar_id/participants/viewer-<id>/remove`, `registrations.room_removed_at`; threat model in `docs/moderation.md`) loses the room for good: their cookie no longer resolves (raise gets 403 `registration_required`), granting their pending hand returns 409, and the removal closes any active hand without a LiveKit call (`HandRaiseControl#drop_hand`) once the expulsion succeeded — if LiveKit fails, the hand stays listed so the host can still revoke the floor, and retrying the removal closes it.

`GET /w/:slug/state` adds generic warning objects only for the owning host when an ended webinar still has unresolved publication permissions. Anonymous viewers and other hosts never receive warnings, personal IDs or SDK errors. Draft-visibility state is accessible to its host alone. Responses use `Cache-Control: no-store`. The end redirect also flashes the warning, and StateButton shows it while retaining the real ended state after a successful transition.

## State and concurrency

The partial unique index permits one active hand per registration. Revoked rows remain history. States: waiting → granting → granted → revoking → revoked. A failed RPC becomes uncertain, preserving honest timestamps; process interruption can leave granting/revoking. Revoke safely reconciles these states because setting can_publish=false is idempotent.

A stable file lock per webinar serializes raise/grant/revoke/end across workers sharing the persistent application storage volume. SQLite transactions are not held across RPC. `Webinar#end!` first commits ended, then attempts revocation of all active hands under that same lock; no later grant can pass. Failed revocations remain uncertain and are logged, while remaining hands are processed. Each RPC has a five-second ceiling; total end latency can scale with the number of failed participants. Retrying the host revoke endpoint is safe after reconnection. A missing/disconnected participant is not falsely recorded as a successful revoke.

This lock is scoped to the application's shared local volume, not independent hosts. A future multi-host app deployment requires a shared coordination mechanism. Reverse-proxy/LiveKit logging and permission policy belong to the existing RoomServiceClient boundary.

## Room UI (2026-10-06)

Two React components consume the endpoints above from `app/javascript/rooms/room.jsx`:

* `HandRaiseViewer` — mounted inside `ViewerLayout` only when the server renders the live room for a confirmed registration (data-attr `data-viewer-hand-raises-url` posted by `webinars/room.html.erb` for `action=viewer` + `@viewer_room`). Button labels follow the server state: `Lever la main` → `Baisser la main` (waiting; « Je préfère observer » with a neutral message for a waiting `wants_video` hand, see above) → `Rendre la parole` (granted). A `ControlBar` with mic/camera toggles is rendered as soon as `useLocalParticipantPermissions().canPublish` becomes true — the LiveKit push is the sole source of truth for publishing readiness; the database `state=granted` only unlocks the button labels. Fail-loud for 403 `payment_required`, 409 `hand_raise_conflict`, 502 `permission_update_failed`, and session expiry.

* `HandRaiseHost` — mounted inside `StageLayout` when the server posts `data-host-hand-raises-url` (only `action=stage`). It polls the host index every 5 s, lists active hands with name + `raised_at` time (French locale), and renders `Donner la parole` / `Retirer la parole` buttons. `uncertain` hands show `Relancer le retrait` (idempotent revoke, reconciles). Grant/revoke URLs are built client-side from the base URL (`<listUrl>/<id>/<verb>`); the server still owns the decision (`authenticate_animateur!` + `host_sub` scope + `find`).

Both components re-use `csrfToken()` from `state_button.jsx` and share the `redirect: "manual"` fail-loud pattern of `recording_control.jsx` (opaque redirect = `session expirée`). Styles live in `app/assets/stylesheets/room.css` under `body.room .lk-hand-raise*` (theme tokens only — no hard-coded hex colour).

Join (`/w/:slug/join?t=…`) deliberately receives neither data-attr: a named speaker already publishes via their speaker token and has no hand to raise or queue to moderate.
